## Этап 1: закрепить проверку — 12 ноября

1. Участник 1 воспроизводит baseline и временной кандидат, делает общий скрипт оценки.
2. Участник 3 параллельно исследует ошибки обоих методов по OOF и формулирует гипотезы.
3. Участник 2 фиксирует текущую модель как контрольный вариант, сверяет финальные ID и подготавливает два сабмита: baseline и текущий лучший кандидат.
4. Команда назначает одного ответственного за Kaggle. Он вручную отправляет baseline и кандидат, записывает время, коммит, файл, его хеш и Public AP. Здесь запланирована отправка; она ещё не выполнена. Учитывать до 10 отправок в день по текущему условию.

Критерий выхода: все сравнивают один и тот же набор строк, известен воспроизводимый локальный результат, есть первоначальная внешняя проверка либо явно записана причина её отсутствия.

## Этап 2: ограниченная серия экспериментов — 13 ноября

Проверяем максимум 2–3 гипотезы из визуального разбора, по одной группе признаков за раз. До запуска записываем, какую ошибку должен исправить признак. Возможные направления, пока без подтверждённого прироста:

- Геометрия человека относительно столов: поможет ли отличить обрезанный торс от допустимого бокса?
- Более аккуратное сопоставление соседей: взаимность/однозначность соответствий, изменение размеров и фактический интервал. Не считать повторение бокса доказательством его правильности.
- Явная обработка отсутствующего контекста в компактной модели, если разбор покажет конкретные сбои.

Сначала сравниваем с текущим кандидатом, затем с baseline, на обоих днях. Предпочитаем улучшение обоих дней. Улучшение среднего с заметным ухудшением одного дня оставляем экспериментальным и документируем компромисс. Не подбираем множество коэффициентов по Public.

Если результат зависит от нескольких кадров, проверяем чувствительность к исключению отдельных кадров или используем bootstrap по кадрам внутри дня. Это диагностика устойчивости, не независимое подтверждение после выбора модели.

Machine pool и признаки публичной модели изображений — резерв. Переходим к ним только при конкретной гипотезе и после работающего основного решения. Машинные боксы не приравниваем к ручным; статистики пула обучаем только на обучающем дне. Для публичных весов сохраняем название и источник.

Критерий выхода: короткая таблица проверенных гипотез, сохранённые OOF и выбранный кандидат. Отрицательные результаты сохраняем, чтобы другие не повторяли те же эксперименты.

## Как передаём результаты

- Признаки: `id,feature_1,...`; один ID — одна детекция, без размножения строк при merge.
- OOF: `id,score` (допустим `day`), с указанием обучения на другом дне. Истинный день проверяющий берёт из датасета.
- Для эксперимента: название, коммит, конфигурация, две дневные AP, среднее, дельта к текущему кандидату, принятое решение.
- Индивидуальные ответы, изображения, токены и датасет остаются локально. В Git — код, агрегированные отчёты и только явно выбранные небольшие модели с метаданными.
- Задача закрывается после передачи результата и проверки критерия готовности, а не только после написания кода.

## Когда остановиться

Если новые признаки не дают устойчивого прироста, сохраняем текущий кандидат и тратим время на воспроизводимость, финальную отправку и объяснение решения. Усложнение модели само по себе не является целью.
