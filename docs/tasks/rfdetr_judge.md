# Задание: RF-DETR как судья другой архитектуры

Исполнитель: Codex на машине Семёна (RTX 5070 Ti). Ветка `codex/redetect-strong`. Время: ~5–6 часов вместе с обучением.
Отправок в Kaggle не делать: отправляет команда. Существующие файлы в `outputs/`, `oof/`, `submissions/` не перезаписывать.

## Зачем

Все шесть голосов D — это YOLO11l: три сида на одних данных, каждый на обычном и отражённом кадре. Они ошибаются
согласованно. Поэтому у людей без вето D почти не отделяет ошибки (26.10: 33% ошибок при возражении против 36% при
согласии). Единственное, что заметно сдвинуло Public, — новые независимые голоса (отражение: 0.90211 → 0.92465).
RF-DETR — другая архитектура (DETR с бэкбоном DINOv2). На малых доменных датасетах после дообучения она заметно
сильнее YOLO11: RF100-VL, AP50:95 — RF-DETR-L 62.2 против YOLO11-L 56.5
([бенчмарк](https://github.com/roboflow/rf-detr/blob/develop/docs/learn/benchmarks.md),
[статья](https://arxiv.org/abs/2511.09554)).

Главный вопрос: **исправляет ли RF-DETR согласованные ошибки YOLO у людей на разных сценах.** Выигрыш на одном человеке
за одним столом не считается.

## Протокол (зафиксирован до просмотра результатов)

Обозначения. `Y` — средний голос шести YOLO (`base s1 s2 base_flip s1_flip s2_flip`), голос = «у бокса заказчика нет
пары один к одному с IoU ≥ 0.6». `R` — голос RF-DETR; если есть отражённый прогон, `R` = среднее обычного и отражённого.
`P` — голос модели позы, `V` — вето, `L` — флаг ног, как в `tools/person_vote.py` с `--skip-window --legs`.

| Вариант | Доля голосов D' | Роль |
|---|---|---|
| Опорный (текущий, Public 0.92465) | все классы: `Y`; люди вне окна: `(6·Y + P) / 7` | точка сравнения |
| **Основной** | `D = (Y + R) / 2`; люди вне окна: `(6·D + P) / 7` | решение об отправке |
| Контрольный | `R` как седьмой голос: `(6·Y + R) / 7`; люди вне окна: `(6·Y + R + P) / 8` | только для понимания чувствительности |

Скор во всех вариантах: `(1 − confidence + D' + 2·max(V, L)) / 4`. Вес позы в основном варианте остаётся 1/7, как
сейчас: меняем одну вещь за раз. Весов не подбирать. Если основной вариант провалился, небольшое преимущество
контрольного не делает его кандидатом.

### Ворота (идти дальше, только если пройдены все предыдущие)

0. **Опорный вариант воспроизводится.** Новый скрипт должен дать для опорного варианта ровно те же AP по дням, что
   `person_vote.py eval --members base s1 s2 base_flip s1_flip s2_flip --skip-window --legs` (ожидаем 0.92579 / 0.92565).
   Расхождение — ошибка в скрипте, искать её, а не идти дальше.
1. **RF-DETR не слабее YOLO по людям.** Для каждого отложенного дня: доля ручных рамок `person`, у которых есть пара
   с IoU ≥ 0.6 среди рамок RF-DETR с уверенностью ≥ 0.3 (сопоставление один к одному). То же для `base`.
   Проходит, если на каждом дне RF-DETR ≥ `base` − 0.10. Иначе его возражения в основном шум — останавливаемся.
2. **RF-DETR даёт новую информацию.** Люди без вето, каждый день отдельно. Таблица:
   число боксов / ошибок / разных кадров для четырёх клеток «большинство YOLO (Y ≥ 0.5) возражает или нет» ×
   «RF-DETR возражает или нет». Отдельно две строки:
   - **исправил**: голос RF-DETR совпал с меткой, а большинство YOLO ошиблось;
   - **испортил**: большинство YOLO право, RF-DETR ошибся.
   Проходит, если по сумме двух дней «исправил» больше «испортил», и исправления есть минимум на 3 разных кадрах.
   Порог R ≥ 0.5 для «возражает».
3. **Основной вариант улучшает общий AP** на всех боксах каждого дня:
   - ни один день не хуже опорного больше чем на 0.005;
   - среднее двух дней выше опорного минимум на 0.003;
   - при исключении любого одного кадра (по очереди все 35) среднее двух дней остаётся выше опорного.
   Плюс парный bootstrap по кадрам (3000 повторов, как в `person_vote.py`): доля повторов с приростом — в отчёт.

Если ворота 1 или 2 не пройдены, финальное обучение не запускать. Остаток времени не тратить на перебор настроек.

## Шаги

### 1. Окружение (отдельное, чтобы не сломать ultralytics)

```bash
python -m venv .venv-rfdetr
.venv-rfdetr/bin/pip install torch torchvision --index-url https://download.pytorch.org/whl/cu128
.venv-rfdetr/bin/pip install rfdetr pandas
```

Брать размер **Medium или Large** (лицензия Apache 2.0). XL/2XL под другой лицензией (PML 1.0) — не брать.
Записать в отчёт точные версии `rfdetr`, `torch` и URL весов, которые скачались при первом запуске.

### 2. Данные в COCO

Новый скрипт `tools/rfdetr_judge.py`, команда `build`. Брать **те же** кадры и рамки, что `redetect.py build`:
классы `CLASSES` (person, nude_hands, cup, tray), ручные рамки через `R.load` (алиас `nude_hand → nude_hands`
применяется там), наборы `day_20261025`, `day_20261026`, `all`.

Раскладка, которую ждёт RF-DETR: `outputs/rfdetr/<набор>/{train,valid,test}/` с картинками и `_annotations.coco.json`.

- **`valid` и `test` — копии `train` того же набора.** Другой день в `valid` класть нельзя: RF-DETR выбирает лучший
  чекпоинт по `valid`, и это будет утечка отложенного дня. Так же сделано у YOLO (`val = тот же набор`).
- Картинки — симлинки на `data/rascar-hack-case-1/<frame_id>.jpg`, координаты из нормированных `cx, cy, w, h` в пиксели
  1280×720.
- Сопоставление id категорий и имён классов проверить вручную на одном кадре: предсказать обученной моделью train-кадр
  и сравнить имена классов с ручными рамками. Имена брать из `detections.data["class_name"]`, если оно заполнено, иначе
  по id из своего JSON. Известная ловушка: смещение id на единицу.

### 3. Обучение дневных моделей

```python
from rfdetr import RFDETRMedium   # или RFDETRLarge, если влезает
model = RFDETRMedium()
model.train(dataset_dir="outputs/rfdetr/day_20261025", output_dir="outputs/rfdetr/runs/day_20261025",
            epochs=EPOCHS, batch_size=2, grad_accum_steps=8, resolution=1120,
            gradient_checkpointing=True, device="cuda")
```

- `resolution` должно делиться на 56. 1120 ближе всего к родным 1280 по ширине. При нехватке памяти — 1008, затем 896.
  Записать, какое взяли.
- `EPOCHS`: замерить время одной эпохи и выбрать так, чтобы одна модель училась **не дольше 40 минут**.
  Одинаковое число эпох для обоих дней и для итоговой модели (на `all` эпоха вдвое дольше — это учтено в бюджете).
- Для предсказаний брать `checkpoint_best_total.pth`: при `valid = train` утечки нет.

### 4. Предсказания

Команда `predict` того же скрипта. Порог `threshold=0.01`, как `conf=0.01` у YOLO. Формат и имена — как у YOLO,
чтобы работал `R.pred_path` с участником `rfdetr`:

- `outputs/redetect_strong/pred_day_20261025_rfdetr.csv` — модель 25.10 на кадрах 26.10;
- `outputs/redetect_strong/pred_day_20261026_rfdetr.csv` — модель 26.10 на кадрах 25.10;
- позже `outputs/redetect_strong/pred_all_rfdetr.csv` — итоговая модель на test.

Колонки: `frame_id,class_name,confidence,x1,y1,x2,y2`, пиксели исходного кадра 1280×720.
Отражённый прогон (`..._rfdetr_flip.csv`, боксы отражать обратно, как `predict --flip` в `redetect.py`) — только если
ворота 2 пройдены и остаётся время.

### 5. Оценка

Команда `eval` того же скрипта. Повторно использовать `R.oof_features`, `R.agreement_features`, `PV.add_signals`,
`PV.scores`, `PV.frame_bootstrap`, а не переписывать сопоставление. Печатает:
ворота 0 (опорный AP), ворота 1 (доля найденных людей), таблицу ворот 2, AP трёх вариантов по дням, исключение
кадров и bootstrap для основного варианта. OOF основного и контрольного вариантов — в `oof/` под новыми именами.
